# 连续跟踪模块目标摘要与详情面板设计

## 1. 背景

现有 `/watch` 模块已经具备：

- 跟踪目标管理（stock / etf / theme）
- 周期性候选买点检测
- 候选事件列表
- 基础事件详情查看

但当前页面仍然缺少两个核心能力：

1. 添加跟踪目标后，用户无法直接看到该目标最近阶段的整体判断。
2. 点击目标后，无法查看对应的 K 线图与策略指标面板。

因此本次设计是在**不新开页面、不推翻现有 `/watch` 主线**的前提下，为现有 watch 页面增加：

- 近 7 个交易日整体分析摘要
- 目标展开后的 `7日 / 30日` K 线与策略详情

## 2. 用户目标

用户期望在现有 watch 可视化里实现以下体验：

- 添加跟踪目标后，列表中直接看到该目标近 7 个交易日的整体分析结果
- 点击跟踪目标后，在当前页面展开详情
- 详情中能查看 K 线图
- 详情中能查看各策略信息，例如均线、MACD、RSI、量价、支撑压力、信号原因和风险因素
- 对 theme 目标，先看到主题整体摘要，再进入某个代表成员的 K 线与策略详情

## 3. 已确认的交互约束

本次需求已确认以下产品决策：

### 3.1 集成位置

- 新能力必须集成到**当前已经存在的 `/watch` 页面**里
- 不新增独立页面，不拆出新的分析中心页面

### 3.2 详情窗口范围

- 展开后的详情支持 `7日 / 30日` 切换
- 推荐默认行为：
  - 列表卡片展示近 7 日整体分析
  - 展开详情默认展示 `7日`
  - 用户可以切到 `30日`

### 3.3 theme 目标表现

- theme 目标需要先显示“主题近 7 日整体分析”
- 展开后默认选中一个代表成员
- 再展示该代表成员的 K 线和策略详情

### 3.4 刷新策略

- 列表摘要会随着后台监测自动刷新
- 展开详情在用户点开时按需加载
- `7日 / 30日` 切换与主题成员切换都按需重新请求详情数据

## 4. 设计目标

本次增量设计的目标是：

1. 在目标列表中增加“近 7 个交易日整体分析摘要”
2. 在当前 watch 页面底部详情区，增加“目标详情”而不是仅展示“事件详情”
3. 支持 `7日 / 30日` K 线切换
4. 支持 theme 目标的“主题摘要 + 代表成员详情 + 成员切换”
5. 保持后台负担可控，不把所有详情都做成后台预计算

## 5. 方案比较

### 方案 A：列表预计算 7 日摘要，详情按需加载 7/30 日

特征：

- 添加目标后立即生成一份近 7 个交易日整体分析摘要
- 列表卡片直接展示这份摘要
- 后台轮询只刷新列表摘要与候选事件
- 用户点击目标时，再按需加载详情
- 详情支持 `7日 / 30日`
- theme 目标先给主题摘要，再默认选中代表成员展开

优点：

- 列表信息完整，符合“先看整体判断”的心智
- 展开详情时仍保持按需计算，避免后台压力过高
- 与现有 `/watch` 页面结构兼容最好

缺点：

- 需要新增摘要快照层
- 添加目标后需要一轮摘要生成过程

### 方案 B：所有内容都随后台轮询统一预计算

特征：

- 每轮后台扫描同时更新列表摘要、详情图表、策略面板
- 用户点击详情时几乎不再需要额外计算

优点：

- 打开详情速度快

缺点：

- 后台计算量明显上升
- theme 展开成员越多，代价越高
- 与当前 watch 轮询职责不匹配

### 方案 C：列表不展示摘要，点击时现算全部内容

特征：

- 后台只负责候选事件监测
- 目标摘要、K 线、策略详情都在点击时临时生成

优点：

- 实现最轻

缺点：

- 列表缺少用户真正想看的“先判断再展开”的信息
- 体验退化明显

### 结论

采用 **方案 A**。

这是唯一同时满足：

- 列表先展示整体分析
- 详情能看 K 线和策略
- theme 有整体摘要
- 后台不过载

## 6. 页面设计

### 6.1 保持当前 `/watch` 页面结构

不重做页面路由，继续沿用：

- 顶部运行状态区
- 中部目标列表区
- 中部候选事件区
- 底部详情区

其中底部详情区从“事件详情”升级为“跟踪详情”。

### 6.2 列表卡片增强

当前目标卡片仅显示：

- 名称
- 类型
- 状态
- 成员数

改造后每个目标卡片增加第二层摘要区，显示：

- 趋势标签
- 综合评分
- 当前建议
- 一句话总结

建议布局：

- 第一行：名称 / 类型 / 状态
- 第二行：近 7 日摘要标签组
- 第三行：简短总结
- 右侧保留“展开详情”按钮

### 6.3 详情区升级为“跟踪详情”

目标详情区包含：

1. 顶部目标信息
2. `7日 / 30日` 切换
3. 主题成员切换（仅 theme 目标需要）
4. K 线图
5. 策略指标区
6. 复核结论区

### 6.4 详情区布局

桌面端建议左右两栏：

- 左栏：K 线图
- 右栏：策略指标与解释

移动端改为上下堆叠：

- 顶部目标信息与切换条
- 中间 K 线图
- 下方策略指标

### 6.5 theme 目标展开方式

theme 目标需要两层信息：

- 主题整体摘要
- 代表成员明细

交互规则：

- 列表卡片先显示主题近 7 日整体摘要
- 展开后默认选中 `representative_member`
- 页面同时提供成员切换条
- 用户切换成员后，仅刷新当前成员的图表与策略信息
- 主题整体摘要不因成员切换而变化

## 7. 后端数据设计

### 7.1 新增快照层而不是污染 `watch_targets`

`watch_targets` 表是目标定义，不应直接塞入运行结果字段。

因此新增：

- `watch_target_snapshots`

用途：

- 保存一个目标当前的 7 日整体摘要快照
- 作为列表卡片展示的主数据源
- 也为 theme 目标保存默认代表成员信息

### 7.2 `watch_target_snapshots` 字段建议

- `id`
- `target_id`
- `summary_window_days`
- `summary_status`
- `summary_signal_score`
- `summary_action`
- `summary_brief`
- `representative_member_code`
- `representative_member_name`
- `payload_json`
- `updated_at`

约束建议：

- `target_id + summary_window_days` 唯一

状态枚举建议：

- `pending`
- `ready`
- `failed`

### 7.4 快照与事件的关系

`watch_target_snapshots` 只保存“目标级摘要”，不直接替代事件表。

职责划分：

- `watch_target_snapshots`
  - 列表卡片级摘要
  - 代表成员选择结果
  - 摘要生成时间
- `watch_signal_events`
  - 候选买点事件
  - 候选事件级复核结果

也就是说，快照和事件是并行存在的两层数据：

- 快照回答“这个目标最近 7 日整体怎么看”
- 事件回答“这个目标最近是否出现了具体候选买点”

### 7.3 payload 内容建议

`payload_json` 中保存结构化摘要，便于前端直接渲染：

- `trend_status`
- `buy_signal`
- `signal_score`
- `signal_reasons`
- `risk_factors`
- `macd_status`
- `rsi_status`
- `volume_status`
- `summary_brief`
- `theme_summary`（仅 theme）

## 8. 服务设计

### 8.1 新增 `WatchSummaryService`

职责：

- 生成目标近 7 个交易日整体分析摘要
- 刷新 `watch_target_snapshots`
- 对 stock/etf/theme 三种目标分别处理

处理方式：

- `stock / etf`
  - 对目标自身做最近 7 个交易日摘要分析
- `theme`
  - 对成员做 7 日分析
  - 聚合出主题整体摘要
  - 选出一个代表成员作为默认详情对象

#### 7 日摘要的明确计算规则

为避免实现歧义，第一版明确如下：

- 摘要窗口使用**最近 7 个交易 bar**，不是自然日；
- 但分析器本身仍可使用最近 30 个交易 bar 作为输入，以保证 MA/MACD/RSI 计算稳定；
- “7 日摘要”的含义是：
  - 结论面向最近 7 个交易日的阶段表现
  - 指标计算允许依赖最近 30 个交易 bar 的历史上下文

具体规则：

- 对 `stock / etf`
  1. 取最近 30 个交易 bar
  2. 用现有 `StockTrendAnalyzer` 计算当前技术状态
  3. 再额外提取最近 7 个交易 bar 的：
     - 区间涨跌幅
     - 近 7 日最高 / 最低
     - 最近 7 日量价变化方向
  4. 将“当前技术状态 + 最近 7 日区间表现”压缩成摘要
- 对 `theme`
  1. 对成员分别执行上述 `stock / etf` 摘要计算
  2. 聚合成员趋势、评分和建议
  3. 生成主题一句话摘要

### 8.1.1 摘要输出结构

第一版 `summary` 必须至少包含：

- `status`
- `trend_status`
- `signal_score`
- `action`
- `brief`
- `buy_signal`
- `period_return_pct`
- `updated_at`

theme 额外包含：

- `representative_member_code`
- `representative_member_name`
- `member_count`

命名约束：

- 存储层可继续使用 `summary_status`
- API 对外统一使用 `summary.status`
- 不向前端直接暴露 `summary_status` 这种存储字段名，避免命名漂移

### 8.2 新增 `WatchDetailService`

职责：

- 按需返回展开面板详情
- 支持 `window=7|30`
- 支持可选 `member_code`

返回内容：

- 目标基础信息
- 当前摘要
- 当前活跃成员
- 可选成员列表
- K 线数据
- 指标数据
- 策略解释
- 最新复核结论

#### `latest_review` 的明确语义

当前系统中的 review 是**事件级**数据，而不是目标级数据。

因此目标详情里的 `latest_review` 第一版必须解释为：

- 当前 `active_member` 最近一个相关事件的最新复核结果

匹配规则：

1. 仅在当前目标范围内查找
2. 仅匹配当前 `active_member`
3. 取该成员最近一个 `watch_signal_event`
4. 再取该事件最新一轮 `watch_review_result`

如果当前成员没有历史候选事件或没有复核结果：

- `latest_review = null`
- 前端显示“暂无复核结论”

不允许把其他成员或主题下别的事件的 review 混入当前成员详情。

### 8.3 现有 `WatchRuntimeService` 的职责调整

保留现有：

- 周期扫描候选事件
- 触发复核
- 发布 SSE

新增：

- 每轮监测后刷新目标 7 日摘要快照

不新增：

- 不在后台统一预计算所有详情图表

### 8.4 初始摘要生成路径

这是本次增量最重要的补充之一。

添加目标后不能依赖“等下一轮 runtime scan 才有摘要”，否则列表首屏体验会明显缺失。

因此第一版必须实现：

- 在 `WatchlistService.create_target()` 成功后，立即触发一次该目标的摘要生成
- 这次摘要生成是**同步或短时阻塞式写入**
- 如果生成成功，返回的目标列表马上可见摘要
- 如果生成失败：
  - 目标仍创建成功
  - 快照状态写为 `failed` 或 `pending`
  - 后续 runtime 周期可自动补刷

推荐做法：

- `WatchlistService` 在创建/刷新成员后调用 `WatchSummaryService.refresh_target_snapshot(target_id)`
- 失败时捕获异常，不回滚目标创建

这样可保证：

- 列表卡片大多数情况下在创建后立即有内容
- 同时不让摘要失败拖垮目标创建主链路

## 9. 接口设计

### 9.1 列表接口增强

现有：

- `GET /api/v1/watch/targets`

增强后列表项需直接带：

- `summary`

这样前端无需再次请求列表摘要。

如果快照尚未生成完成，列表项中的 `summary` 仍要返回稳定结构：

```json
{
  "status": "pending",
  "signal_score": null,
  "action": null,
  "brief": "摘要生成中"
}
```

如果快照生成失败：

```json
{
  "status": "failed",
  "signal_score": null,
  "action": null,
  "brief": "摘要生成失败"
}
```

如果快照生成成功：

```json
{
  "status": "ready",
  "signal_score": 68,
  "action": "买入",
  "brief": "近 7 日趋势偏强，可继续跟踪"
}
```

### 9.2 新增目标详情接口

建议新增：

- `GET /api/v1/watch/targets/{id}/detail?window=7`
- `GET /api/v1/watch/targets/{id}/detail?window=30`

对于 theme，还应支持：

- `GET /api/v1/watch/targets/{id}/detail?window=30&member_code=300308`

### 9.3 详情返回结构建议

```json
{
  "target": {},
  "summary": {},
  "member_options": [],
  "active_member": {},
  "kline": [],
  "indicators": {},
  "strategy_insights": {},
  "latest_review": {}
}
```

字段说明：

- `target`: 当前目标
- `summary`: 列表用的近 7 日整体摘要
- `member_options`: theme 成员列表；stock/etf 可为空或单元素
- `active_member`: 当前正在展示详情的成员
- `kline`: K 线数组
- `indicators`: MA/MACD/RSI/量价/支撑压力
- `strategy_insights`: signal reasons / risk factors / 当前建议
- `latest_review`: 最近一轮复核结论

补充约束：

- `latest_review` 绑定的是当前 `active_member`
- 不是整个目标的全局最新 review
- 不是主题下任意成员的最新 review

## 10. 计算与刷新策略

### 10.1 添加目标时

推荐行为：

- 先快速创建目标
- 创建完成后立即触发一次目标级摘要生成
- 默认优先尝试同步生成并保存快照
- 若摘要生成失败，则列表初始显示“摘要生成中”或“摘要生成失败”
- 后续再通过后台轮询补刷

接口约定：

- `POST /api/v1/watch/targets` 第一版不强制直接返回完整 `summary`
- 前端在创建成功后统一重新请求 `GET /api/v1/watch/targets`
- 这样可以复用同一套列表项结构，避免创建接口和列表接口出现双份摘要装配逻辑

### 10.2 后台监测轮次

后台每轮自动刷新：

- 目标 7 日摘要
- 候选事件

后台不自动刷新：

- 每个目标的展开详情
- 每个窗口的 K 线图
- 每个成员的完整策略面板

### 10.3 展开详情时

- 用户点击目标时按需加载详情
- 默认请求 `window=7`
- 用户切换到 `30日` 时单独重新请求
- 用户切换成员时重新请求该成员详情

## 11. K 线与策略信息范围

### 11.1 K 线数据

展开详情时应返回：

- `date`
- `open`
- `high`
- `low`
- `close`
- `volume`

窗口：

- `7日`
- `30日`

### 11.2 策略指标

详情区至少显示以下已存在的策略信息：

- 趋势状态
- 综合评分
- 买入信号
- MA5 / MA10 / MA20
- MACD 状态
- RSI 状态
- 量价状态
- 支撑位 / 压力位
- signal reasons
- risk factors

### 11.3 复核信息

详情区补充：

- 最新复核建议
- 置信度
- 一句话复核总结

## 12. theme 摘要聚合规则

第一版不做复杂权重模型，采用简单聚合规则：

- 成员摘要各自计算
- 主题摘要从成员结果中聚合：
  - 趋势标签采用多数决
  - 评分取均值或加权均值
  - 一句话摘要采用模板化聚合
- 代表成员选择优先级：
  1. snapshot 中已记录代表成员
  2. 优先 ETF
  3. 再退回第一个股票成员

## 13. 性能边界

### 13.1 必须控制的数据量

- 列表接口不返回 K 线数组
- 详情接口一次只返回：
  - 一个目标
  - 一个窗口
  - 一个成员

### 13.2 不做的预计算

第一版明确不做：

- 全目标全成员图表预缓存
- 多窗口图表一次性全部生成
- 一次性返回 theme 所有成员的完整详情

### 13.3 出错降级

- 摘要生成失败：目标列表显示失败态，允许后续轮次重刷
- 详情加载失败：仅详情区报错，不影响列表和候选事件
- theme 无代表成员：主题摘要仍显示，详情区显示“暂无可展示成员”
- K 线数据不足：照常显示已有 bars，并提示样本不足

## 14. 最小落地范围

本次增量只落地：

1. 列表卡片新增近 7 日整体分析摘要
2. 目标点击后展开“跟踪详情”
3. 详情支持 `7日 / 30日`
4. 详情支持 K 线图
5. 详情支持策略指标区
6. theme 目标支持“主题摘要 + 默认代表成员 + 成员切换”

暂不落地：

- 多图并排
- 用户自定义指标显隐
- 导出图片
- 60 日 / 120 日窗口切换

## 15. 推荐实施顺序

1. 扩展存储层：新增 `watch_target_snapshots`
2. 新增 `WatchSummaryService`
3. 新增 `WatchDetailService`
4. 增强 `GET /api/v1/watch/targets`
5. 新增 `GET /api/v1/watch/targets/{id}/detail`
6. 升级 `/watch` 前端页面卡片与详情区
7. 补测试、文档与验证
